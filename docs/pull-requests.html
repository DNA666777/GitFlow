Le mode Pull Request

Une option du Finish pour les dépôts où master et develop sont protégées : au lieu de merger en local, l'extension pousse la branche et ouvre les pull requests. La revue et le merge restent humains.

Le choix se fait à chaque Finish dans la boîte Terminer. Pour pré-sélectionner Pull Request sur un dépôt, réglez « Mode de Finish par défaut » dans les paramètres.

Prérequis

  • Le remote origin pointe vers GitHub (github.com) ou Azure DevOps (dev.azure.com ou *.visualstudio.com), en https ou en ssh.
  • Git connaît déjà vos identifiants : si vous avez déjà fait un push ou un fetch en https sur ce serveur (depuis Visual Studio ou un terminal), c'est le cas. L'extension les demande à git (git credential fill, en pratique au Git Credential Manager). Elle n'en stocke aucun, et ils n'apparaissent jamais dans les logs.
  • Aucun outil supplémentaire : ni gh, ni az.
« Aucun identifiant git pour dev.azure.com »

Connectez-vous une fois en lançant dans un terminal git ls-remote <url du dépôt> : la fenêtre de connexion du Git Credential Manager s'ouvre. Ensuite, réessayez.

Une feature par PR

  1. Démarrez et développez la feature comme d'habitude (guide).
  2. Terminer… : choisissez Pull Request. Les options de push et de suppression sur origin disparaissent : elles ne servent pas en mode PR.
  3. L'écran suivant montre le titre et la description générés, modifiables, pour chaque PR.
  4. OK : l'extension pousse la branche puis crée la PR feature/x → develop. S'il en existe déjà une ouverte, elle est réutilisée et vos nouveaux commits y arrivent. Rien n'est mergé en local.
  5. Faites relire et mergez la PR sur la plateforme (merge sans fast-forward de préférence, voir squash).
  6. Dans la fenêtre GitFlow : Actualiser les PR puis Finaliser la branche.

Le message généré

Construit uniquement depuis git (déterministe, sans IA). Le titre suit la convention Feature: nom / Release 1.5.0 / Hotfix 1.5.1. La description :

**Feature** `feature/ABC-12-login` → `develop`

### Commits (2)
- Ajoute la page de connexion
- Corrige le style du bouton (#42)

### Fichiers
5 fichier(s) modifié(s), 120 ligne(s) ajoutée(s), 8 ligne(s) supprimée(s)

### Tickets
ABC-12, #42

Pour une release ou un hotfix, une section Version rappelle le tag qui sera créé après le merge.

Personnaliser

  • Votre modèle : .gitflow/pull_request_template.md dans le dépôt, avec les variables {type} {source} {target} {commits} {stats} {version} {tickets}.
  • Le modèle de la plateforme (.github/pull_request_template.md, .azuredevops/pull_request_template.md…) est utilisé comme base : la description générée est ajoutée en dessous.
  • Motif des tickets : clé gitflowvs.pr.ticketpattern (expression régulière). Par défaut ABC-123 et #42.

Une section Pull requests apparaît dans la fenêtre dès qu'une PR est suivie : une ligne par PR, avec son état (ouverte, mergée, fermée sans merge) et un bouton Ouvrir vers le navigateur.

L'état est lu sur la plateforme au plus une fois par minute quand la fenêtre est visible, ou immédiatement avec Actualiser les PR.

L'extension n'approuve ni ne merge jamais une PR.

Release et hotfix : le tag

Une release ouvre deux PR : vers master et vers develop. Un hotfix aussi, vers master puis vers develop (ou vers la release en cours).

Le tag ne peut être créé qu'une fois la PR vers master mergée, sur son commit de merge :

  1. Mergez la PR vers master sur la plateforme.
  2. Actualiser les PR : le bouton Créer le tag 1.5.0 apparaît.
  3. L'extension fait un fetch de master, vérifie que le commit de merge est bien sur origin/master, crée le tag annoté (avec le message saisi au Finish) et le pousse.

Finaliser la branche crée aussi le tag s'il manque, si les deux PR sont déjà mergées.

Finaliser la branche

Quand toutes les PR d'une branche sont mergées, Finaliser la branche :

  1. crée le tag s'il s'agit d'une release ou d'un hotfix et qu'il manque ;
  2. fait un git fetch (ou git fetch --prune si l'option est cochée dans les paramètres) ;
  3. met à jour vos develop / master locales, en fast-forward uniquement ;
  4. supprime la branche locale avec git branch -d et oublie ses PR ;
  5. vous laisse sur develop (ou sur la release en cours).
Merge par « squash » ou « rebase »

Dans ce cas, les commits de votre branche ne sont pas dans develop : l'extension le détecte et ne supprime pas la branche. Supprimez-la vous-même si vous êtes sûr. Pour éviter ça, choisissez le merge classique (Merge / Merge (no fast-forward)).

Branches sur le serveur

Finaliser ne supprime pas la branche sur le serveur : cochez Delete branch after merging (Azure) ou activez Automatically delete head branches (GitHub). Avec l'option git fetch --prune, les références origin/… correspondantes disparaissent ensuite toutes seules de votre poste.

Avec un remote ssh, l'extension demande quand même des identifiants https au Git Credential Manager pour appeler l'API : connectez-vous une fois en https si besoin.

Serveur Azure DevOps d'entreprise

Les URL d'un serveur Azure DevOps installé dans l'entreprise (Azure DevOps Server, anciennement TFS) ne peuvent pas être reconnues automatiquement, par exemple https://tfs.entreprise.com/tfs/Collection/Projet/_git/Repo. Dans ce cas, cochez « Pull Request : origin est un serveur Azure DevOps » dans les paramètres.

  • L'URL doit contenir /_git/ : l'API est appelée sur la partie qui précède (collection et projet).
  • Authentification : les identifiants que git connaît pour ce serveur (jeton personnel) s'il y en a, sinon votre session Windows, comme git lui-même dans un réseau d'entreprise.
  • API REST 4.1 : compatible à partir de TFS 2018.
  • Avec un remote ssh, l'API est appelée en https sur le même serveur.
