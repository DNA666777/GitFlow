Référence et dépannage

Les règles appliquées, les clés de configuration et les réponses aux problèmes courants.

Le modèle en bref

L'extension applique strictement le Gitflow Workflow d'Atlassian, sans variante. Seule différence : la branche de production s'appelle master par défaut (configurable).

TypePréfixePart deSe termine dansTagVersion proposée
Featurefeature/developdevelopnon—
Releaserelease/developmaster puis developouiminor + 1 (1.4.1 → 1.5.0)
Hotfixhotfix/mastermaster puis develop (ou la release en cours)ouipatch + 1 (1.5.0 → 1.5.1)
  • Aucun autre type de branche (pas de bugfix/, support/…).
  • Merges en --no-ff, sans squash ni rebase. Tags annotés {préfixe}{version}, message Release x.y.z / Hotfix x.y.z modifiable.
  • Une seule release et un seul hotfix en cours à la fois.

Règles de sécurité

Modifications non commitéesStart et Finish refusés. L'extension ne fait jamais de stash automatique : faites un commit ou un git stash vous-même. Les fichiers non suivis ne bloquent pas.
Vérifications avant d'agirBranche de base existante, nom valide pour git (git check-ref-format), branche cible inexistante, tag inexistant.
Conflit de mergeArrêt immédiat, rien n'est supprimé, reprise possible après résolution.
Commandes interditesJamais de push --force, reset --hard, branch -D. Une branche non mergée n'est jamais supprimée.
CommitsRefusés sur la branche de production et pendant un merge.
Pull RequestsCréées et suivies, jamais approuvées ni mergées par l'extension. Le tag n'est créé que sur un commit de merge vérifié sur origin/master.
IdentifiantsDemandés à git à chaque fois, jamais stockés ni écrits dans les logs.

Clés de configuration

Stockées dans la git config du dépôt (--local) ou de l'utilisateur (--global, valeurs par défaut des nouveaux dépôts). La valeur locale l'emporte.

Commandes git exécutées

Toutes les commandes passent par le git de Git for Windows : vos hooks, signatures GPG, LFS et identifiants s'appliquent comme dans un terminal. Elles sont visibles dans Affichage > Sortie, canal GitFlow :

=== GitFlow : finish de feature/login ===
[10:42:03] git switch develop  → 0 (81 ms)
[10:42:03] git merge --no-ff -m "Merge branch 'feature/login' into develop" feature/login  → 0 (153 ms)
[10:42:03] git branch -d feature/login  → 0 (54 ms)
OK

Dépannage

Le menu GitFlow n'apparaît pas

Vérifiez Extensions > Gérer les extensions > Installées. Si l'extension n'y est pas, réinstallez le .vsix avec Visual Studio fermé : s'il est ouvert, le Visual Studio Installer se ferme sans rien installer.

Un clic ne fait rien

Regardez le canal GitFlow de la fenêtre Sortie, puis le journal de l'extension : %TEMP%\servicehub\logs\*GitFlow.VSExtension*.log.

« Aucun dépôt Git trouvé »

L'extension cherche le dépôt à partir de la solution ouverte, puis de l'élément sélectionné, puis du document actif. Ouvrez une solution située dans un dépôt Git.

« Des modifications ne sont pas commitées »

Faites un commit (section Commit) ou un git stash, puis réessayez. Les fichiers non suivis ne comptent pas.

Mes fichiers modifiés n'apparaissent pas dans Commit

Enregistrez-les (Ctrl+S) : git ne voit que les fichiers écrits sur le disque.

La release proposée a déjà un tag

La version suivante est calculée depuis le plus grand tag de version présent sur master. Tapez une autre version : un tag existant est refusé.

« Mode Pull Request indisponible »

Le remote origin n'est ni GitHub ni Azure DevOps (un dossier local, GitLab, Bitbucket…) : utilisez le merge local. Vérifiez l'URL avec git remote -v.

« La plateforme a refusé la demande »

Le message de GitHub ou d'Azure DevOps est affiché tel quel : droits insuffisants, PR déjà existante, branche cible absente… Après correction, relancez Terminer… : une PR ouverte existante est réutilisée.

Finaliser refuse : branche non contenue dans develop

La PR a été mergée par squash ou rebase : les commits de la branche ne sont pas dans develop. Rien n'est supprimé. Si le contenu est bien livré, supprimez la branche vous-même : git branch -D feature/x.

Compatibilité

Visual Studio2022 version 17.14 ou plus, 2026 (18.x). Éditions Community, Professional, Enterprise.
GitGit for Windows 2.28 ou plus (installé avec Visual Studio)
Plateformes (mode PR)GitHub (github.com), Azure DevOps (dev.azure.com, *.visualstudio.com)
LanguesAnglais (par défaut) et français, selon la langue de Visual Studio. Les messages générés (commit, PR) suivent la même langue.
ConfigurationCompatible avec les clés gitflow.* de git-flow / git-flow-avh
