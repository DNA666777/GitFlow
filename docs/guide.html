Guide d'utilisation

Tout ce qu'il faut pour travailler en Gitflow depuis Visual Studio : installer, initialiser, puis faire vivre features, releases et hotfixes.

1. Installation

  1. Fermez complètement Visual Studio (toutes les fenêtres). Sinon l'installateur se ferme sans rien installer.
  2. Double-cliquez sur GitFlow.VSExtension.vsix. Selon la version de Visual Studio, le VSIX Installer puis le Visual Studio Installer prennent la main : validez jusqu'au bout.
  3. Relancez Visual Studio. Le menu Extensions > GitFlow apparaît, et l'extension est listée dans Extensions > Gérer les extensions > Installées.

En ligne de commande, l'équivalent est :

& "C:\Program Files\Microsoft Visual Studio\18\Enterprise\Common7\IDE\VSIXInstaller.exe" GitFlow.VSExtension.vsix
Mise à jour

Même procédure avec le nouveau .vsix. Pour désinstaller : Extensions > Gérer les extensions, puis Désinstaller.

2. La fenêtre GitFlow

Ouvrez-la par Extensions > GitFlow > Fenêtre GitFlow (ou Affichage > Autres fenêtres). Elle s'ancre en onglet à côté de Git Changes et se met à jour toute seule : à l'enregistrement d'un fichier, au changement de branche, à l'ouverture d'une autre solution.

Ce que montre la fenêtre

  • L'état du dépôt : branche courante et son type, arbre propre / modifié / merge en cours, commits à pousser ou à récupérer.
  • Commit : fichiers modifiés et message proposé (détails).
  • Démarrer une branche : type, préfixe, nom. Pour une release ou un hotfix, la version suivante est pré-remplie.
  • Branches en cours, groupées par type, avec Publier et Terminer… sur chaque ligne : pas besoin d'être sur la branche pour la terminer.
  • Les badges courante et déjà mergée (une branche mergée à la main dans toutes ses cibles).
  • Sur une branche release/, le rappel « corrections, docs et tâches de release uniquement ».
  • La section Pull requests apparaît si vous utilisez le mode Pull Request.

3. Initialiser un dépôt

Sur un dépôt qui n'a jamais utilisé GitFlow, la fenêtre propose Initialiser GitFlow…. L'écran de paramètres s'ouvre, pré-rempli :

  • avec la configuration git-flow existante si le dépôt en a déjà une (elle est reprise telle quelle) ;
  • sinon avec vos réglages « Tous mes dépôts » ;
  • sinon avec les valeurs standard : master, develop, feature/, release/, hotfix/, préfixe de tag vide.

À la validation, la branche develop est créée depuis master si elle n'existe pas (ou depuis origin/develop si elle existe sur le serveur), et la configuration est écrite dans le dépôt (clés standard gitflow.*, compatibles avec les autres outils git-flow).

Le dépôt doit avoir au moins un commit

Sur un dépôt vide, faites d'abord un premier commit sur master.

4. Une feature de A à Z

Une feature part de develop et y revient. Elle ne touche jamais master.

Démarrer

  1. Dans Démarrer une branche, choisissez Feature et tapez un nom, par exemple login ou ABC-123-login.
  2. Démarrer : la branche feature/login est créée depuis develop et extraite.

Refus possibles, avec un message en français : arbre de travail sale, nom invalide pour git, branche déjà existante (en local ou sur origin), merge en cours.

Publier (optionnel)

Publier pousse la branche sur origin (git push -u origin feature/login) pour la partager ou la sauvegarder. Seuls les commits partent : pensez à commiter avant.

Terminer

Terminer feature/login✕

Terminer… ouvre cette boîte. En merge local (le mode par défaut) :

  1. merge --no-ff de la feature dans develop, pour garder la trace de la branche dans l'historique ;
  2. suppression de la branche locale avec git branch -d, que git refuse si elle n'est pas mergée ;
  3. en option : push de develop vers origin, suppression de la branche sur origin ;
  4. vous êtes ramené sur develop.

Les deux cases peuvent être pré-cochées dans les paramètres.

5. Commiter

La section Commit de la fenêtre liste les fichiers modifiés (A ajouté, M modifié, D supprimé, R renommé) et propose un message construit uniquement à partir de git, sans IA, toujours identique pour les mêmes modifications.

Met à jour 2 fichiers

Ajoutés (1) :
- src/Login.cs
Modifiés (1) :
- README.md (+2 -1)

Réf. : ABC-12        ← tickets trouvés dans le nom de branche (ABC-123, #42)
  • Quoi est commité : si des fichiers sont déjà indexés (git add), seulement eux ; sinon tout, nouveaux fichiers compris, comme « Commit All ».
  • Le message est à vous : dès que vous le modifiez, il n'est plus remplacé. Régénérer le message remet la proposition.
  • Réécrivez la première ligne pour les gros commits : le générateur sait quels fichiers ont changé, pas pourquoi.
  • Les fichiers apparaissent après enregistrement (Ctrl+S) : git ne voit pas une modification encore dans l'éditeur.
Commits refusés

Sur master (on ne commite jamais directement en production : démarrez une feature ou un hotfix) et pendant un merge en conflit (le commit reviendrait à finir le merge à la place du Finish).

6. Une release

Quand assez de features sont dans develop, une release les prépare pour la production. Sur la branche de release : corrections, documentation et tâches de release uniquement, plus de nouvelles features.

  1. Démarrer une branche > Release : la version suivante est proposée en incrémentant le minor du dernier tag de master (1.4.1 → 1.5.0). Modifiable.
  2. Si develop ne contient rien de nouveau depuis la dernière release, un avertissement s'affiche : la release serait identique à la précédente. Vous pouvez continuer quand même.
  3. Faites vos derniers ajustements (numéro de version, changelog…) et commitez.
  4. Terminer… : le message du tag est proposé (Release 1.5.0), modifiable.

Le Finish d'une release, dans l'ordre :

  1. merge --no-ff dans master ;
  2. tag annoté 1.5.0 sur master (ou v1.5.0 avec le préfixe v) ;
  3. merge --no-ff dans develop ;
  4. suppression de la branche, retour sur develop.
Astuce

Cochez « Pousser » pour envoyer master, develop et le tag en une fois.

7. Un hotfix

Un problème en production ? Le hotfix est la seule branche qui part directement de master.

  1. Démarrer une branche > Hotfix : version proposée = patch du dernier tag + 1 (1.5.0 → 1.5.1).
  2. Corrigez, commitez.
  3. Terminer… : merge dans master + tag, puis merge dans develop.
Hotfix pendant une release

Si une branche release/ est en cours, le hotfix est mergé dans master puis dans la release au lieu de develop : la correction rejoindra develop au Finish de la release.

Il ne peut y avoir qu'une release et qu'un hotfix en cours à la fois.

8. Conflits et reprise

Si un merge du Finish rencontre un conflit, l'extension s'arrête immédiatement et ne supprime rien. Le message liste les fichiers en conflit, et le dépôt reste dans l'état de merge.

  1. Résolvez les conflits (éditeur de fusion de Visual Studio ou à la main) et enregistrez.
  2. Marquez les fichiers comme résolus : Indexer dans Git Changes, ou git add <fichier>.
  3. Ne commitez pas vous-même : cliquez sur Reprendre le finish… dans la fenêtre (ou relancez Terminer…).

Le Finish conclut le merge, saute les étapes déjà faites (merge dans master, tag) et termine le reste.

Le merge a déjà été conclu par Visual Studio ?

Pas de problème : la branche apparaît avec le badge déjà mergée. Terminer… sur sa ligne posera le tag s'il manque et la supprimera.

Pour tout annuler à la place : git merge --abort.

  • Portée : Ce dépôt (git config locale) ou Tous mes dépôts (git config globale, valeurs par défaut des nouveaux dépôts).
  • Seul le nommage est configurable, pas le comportement du flow.
  • Préfixe de tag : vide par défaut (tags 1.4.0), ou v (tags v1.4.0).
  • Validation en direct : préfixe vide ou en double, production = développement. Les noms refusés par git sont signalés à l'enregistrement, et rien n'est écrit.
  • Changer un préfixe ne renomme pas les branches existantes : un avertissement les liste avant d'enregistrer.

Toutes les clés sont décrites dans la référence.
